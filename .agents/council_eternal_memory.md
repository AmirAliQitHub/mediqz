## 3. IDENTIFIED DEFECT IN AUTO ROUTINE SORTER
- **Current Defect:**
  1. Destructive Overwrite: Calling `handleApply` wipes out all existing items across all days in `useRoutineStore`, destroying schedules previously built for other courses.
  2. Part Truncation & Math Flaw: Parts are iterated sequentially up to `durationDays * partsPerDay`. If a course has 15 parts and user sets 7 days @ 2 parts/day, only 14 parts are scheduled and the 15th part is silently dropped! Conversely, if a course has 6 parts and 7 days are created, the last day is an empty dead zone.
  3. No Merge/Append Choice: Students cannot choose whether to "جایگزینی کل برنامه" (Replace All) or "افزودن و چینش در روزهای موجود" (Append / Distribute into existing days).
  4. Missing Course Part Telemetry: Student cannot see how many parts exist in the chosen course or how many days are mathematically required before confirming.

## 6. MODULE 7 SCOPE: DYNAMIC JALALI ENGINE & SMART ROUTINE SORTER RE-ARCHITECTURE
- **Phase 1: Dynamic Jalali Calendar Engine & Cache Invalidation:**
  - Root Cause: `useRoutineStore.ts` cached the entire `days` array in `localStorage` (`mediaz_routine_days_v1`) including static `title`, `is_today: true`, and `shamsi_date`. On day rollover (e.g. from 12 Aban to 13 Aban), it reloaded the stale array without recomputing today's date or shifting `is_today` to the actual date.
  - Fix: Decouple routine items from day tab metadata. Store items by standard Shamsi date string (`YYYY-MM-DD`). On store initialization or day check, dynamically re-anchor days against `getEffectiveStudyDate()`. Compute `is_today`, `is_past`, `is_future`, and Persian titles in real-time.
- **Phase 2: Mobile Viewport & Liquid-Glass Popup Architecture:**
  - Root Cause: Popup rendered inside DOM sub-hierarchy with `items-end`, prone to overflow truncation and 10% bottom-screen clipping on Telegram WebApp. Background was opaque `bg-slate-950/95` and muddy black `bg-black/70`.
  - Fix: React Portal to `document.body` with `fixed inset-0 z-[9999]`. Use `100dvh` container with standard bottom-sheet / modal height (80-85dvh) with internal scroll (`overflow-y-auto overscroll-contain`). Replace muddy black with project standard liquid glass: semi-transparent backdrop blur (`backdrop-blur-md bg-slate-950/40`) and modal card in deep translucent purple glass (`bg-[#110d26]/85 backdrop-blur-2xl border border-purple-500/25 text-white`).
- **Phase 3: 4-Step Streamlined Smart Sorter Workflow & Continuous Repetition Algorithm:**
  - Strip obsolete options (cram, leitner odd/even, fixed duration presets).
  - Step 1: Course Selector (auto-detects total parts from course metadata, zero hardcoding).
  - Step 2: Start Date Picker (from today forward in Shamsi) & Live Reactive End Date Display.
  - Step 3: Daily Part Quota ($P$ parts per batch).
  - Step 4: Continuous Repetition Mode ($R$ days repeat):
    - If toggled ON, shows input for $R$ (repetition days).
    - Algorithm: Each batch of $P$ parts is scheduled on day $T$ (initial study), then repeated identically on days $T+1, \dots, T+R$. Total days per batch = $1 + R$. Next batch starts on day $T + R + 1$.
    - If toggled OFF ($R = 0$), each batch takes 1 day.

## 8. MODULE 8 SCOPE: AUTHENTICATION, TELEGRAM WEBAPP VALIDATION, MAGIC LOGIN & 1-TO-1 ACCOUNT LINKING
- **Problem Diagnostics:**
  1. TWA Silent Re-Registration Bug: `get_or_create_telegram_user` was overwriting user's custom `display_name` with raw Telegram first name on every launch, and onboarding modal lacked non-Telegram username/password configuration, leaving users unable to log in on desktop.
  2. Missing Laptop Magic Login: Iranian students without desktop Telegram had to manually remember and type passwords; a Telegram bot approval mechanism was completely absent.
  3. Disjoint Web/Telegram Accounts: A student registering on desktop had no clean way to link their Telegram account when later opening the Mini App, risking duplicate empty profiles.
- **Architectural Solution:**
  - **HMAC-SHA256 InitData Cryptographic Validation:** FastAPI endpoint `/api/auth/telegram-webapp` parses and verifies Telegram hash against `bot_token`.
  - **Mandatory Non-Telegram Credentials Setup:** Both web registration and Telegram first-time onboarding require setting a unique `username` (verified via `/api/auth/check-username`) and `password` (min 4 characters), ensuring desktop access is always guaranteed.
  - **Telegram Magic Login Engine (`magic_login_requests` table):**
    - Desktop requests login with identifier -> server creates 120s TTL nonce -> bot sends inline keyboard push to user's Telegram chat (`✅ تایید ورود به لپ‌تاپ` / `❌ رد درخواست`).
    - Webhook receives callback query, verifies `from_user.id == telegram_user_id`, sets status to `approved`, and issues session token.
    - Desktop polls `/api/auth/magic-login/poll?nonce=...` and logs in automatically.
  - **1-to-1 Account Linking & Collision Defense:**
    - Each Telegram account is bound to exactly 1 user profile (`UNIQUE(telegram_user_id)`).
    - If an unlinked desktop user opens TWA, they can link their existing credentials seamlessly via modal confirmation.
    - Profile management displays linked Telegram status with link/unlink safeguards.
